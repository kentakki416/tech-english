## 着手トリガー

- 長文読解の継続利用が確認でき、**1〜2 分で終わる短いメニュー** の要望が出た（mobile のすき間時間向け）
- 調べた単語（`attempt_word_lookups`）がユーザーあたり 100 語程度たまり、個人の単語帳として出す価値が出た
- 用語集（`passage_glossary_entries`）が数千語句たまり、問題の材料が十分にある

## 対象範囲

| | MVP | 着手後 |
| --- | --- | --- |
| 長文読解 | ✅ | ✅（変わらない） |
| 単語問題 | ❌ | 用語集と調べた単語から 4 択を作る |
| 文法問題 | ❌ | 本文の実際の文から穴埋めの 4 択を作る |
| 単語帳（調べた単語の一覧） | 挑戦ごとの結果画面にだけ出す | 全挑戦を横断した一覧と復習 |
| 学習記録 | 長文読解の挑戦だけを数える | 単語・文法の回答も学習した日と学習時間に含める |

## 単語問題

**材料は MVP で既にためているデータを使う。** 新しく LLM で単語を集める必要はない。

| 材料 | 使い方 |
| --- | --- |
| `passage_glossary_entries` | 語句・見出し語・**文脈での意味**・その語句が出てきた本文の文。「この文での `opt out of` の意味は？」の 4 択を作れる |
| `attempt_word_lookups` | ユーザーが実際に調べた語句。**その人専用の出題** に使う |

設計案：

- 出題形式：本文の 1 文を示し、語句の文脈での意味を 4 択で選ぶ（誤りの選択肢は同じ品詞の別の用語集の意味から選ぶ）
- 出題の順番：調べた語句を優先し、間違えた語句は間隔を空けて再出題する（間隔反復。最初は「1 日後 → 3 日後 → 7 日後」の固定間隔で十分）
- 1 回 10 問・1〜2 分程度
- 問題の生成は不要（DB のデータから出題時に組み立てる）ため、管理者の承認フローは要らない。ただし用語集は管理者が承認したものだけを使う

## 文法問題

- 材料：公開済みの問題の本文の文。実際の技術文書の文なので、「技術文書でよく出る文法」（受動態、関係詞、仮定法、`should` / `may` の使い分け、冠詞）を自然に扱える
- 生成：`generate:questions` とは別のタスク（`generate:grammar-drills`）で、本文の文を選んで穴埋めの 4 択を LLM で作る。長文読解と同じく **管理者の承認を経て公開** する（文法の正解の誤りは長文以上に信頼を損なうため）
- 出題形式：文の一部を空欄にし、4 つの候補から選ぶ。解説で文法のポイントを説明する

## 学習記録との統合

長文読解の挑戦（`reading_attempts`）とは別のテーブル（例：`drill_sessions` / `drill_answers`）に記録し、**学習記録の集計で合算する**。

- `reading_attempts` に種別の列を足して混ぜる案は採らない。長文読解の挑戦は「本文・制限時間・アシスト」を持ち、単語・文法とは持つ情報がほとんど違うため
- 学習記録の集計（[learning-record](../learning-record/README.md#集計の方法)）を、2 つのテーブルの `UNION ALL` に変える。日ごとの集計テーブルへの切り替えを先に行っておくと楽になる

## 既存仕様との差分（着手時のチェックリスト）

- [ ] `learning-record`：「学習した日」の定義を「長文読解の挑戦を提出した日」から「いずれかの学習を終えた日」に変える。カレンダー・連続日数・週の目標（問題数の数え方）を見直す
- [ ] `learning-record`：`GOAL_METRICS` の「問題数」に単語・文法を含めるかを決める
- [ ] `question-generation`：文法問題の承認フローを admin に追加する（状態の定義を流用できるか確認）
- [ ] `reading-practice`：結果画面の「調べた単語」から単語帳・単語問題への導線を足す
- [ ] `passage_glossary_entries (lemma)` の index が出題の検索に足りているか確認する
- [ ] mobile のタブ構成（マイページ / 問題 / 設定）に「単語・文法」をどう置くかを `design-mock` で決める
