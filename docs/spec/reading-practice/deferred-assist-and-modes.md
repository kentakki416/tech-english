## 任意の文の翻訳

### 着手トリガー

- 段落の和訳では粒度が粗く、「この 1 文だけ訳を見たい」という要望が多い
- 段落の和訳を見る割合が高く、文単位に分けた方が学習効果が高いと判断した

### 対象範囲

| | MVP | 着手後 |
| --- | --- | --- |
| 段落の和訳 | 事前生成 | 事前生成（変わらない） |
| 文の和訳 | ❌ | 文をタップ（長押し）で表示 |

### 設計案

2 つの案がある。**まず案 A を検討する**（費用と待ち時間が発生しないため）。

| 案 | 内容 | 待ち時間 | 費用 |
| --- | --- | --- | --- |
| A | 生成時に文単位の和訳も作っておく（段落の和訳を文に分けて対応づける） | なし | 生成時のみ（出力トークンが増える） |
| B | 解答中に LLM をその場で呼び、`(passage_id, block_index, 文のハッシュ)` で結果をキャッシュして全ユーザーで共有する | 初回 1〜3 秒 | 初回のみ |

案 B を採る場合は、ユーザーごとの 1 日の上限（例：50 回）と、管理者の承認を経ない訳を表示することの注記が必要。

### 既存仕様との差分（着手時のチェックリスト）

- [ ] `PassageBlock` に文の区切りと文ごとの和訳を持たせる（案 A）。question-generation のプロンプトと公開の条件を更新
- [ ] アシストの使用の記録に「文の和訳を見た回数」を足す（`reading_attempts`、結果画面、マイページ）
- [ ] mobile の長押し（段落の和訳）と、文のタップの操作が衝突しないかを決める

## 範囲選択した語句の意味

- web（PC）は `selectionchange` で選択範囲を取得できるため実現できる。mobile アプリ（RN）は `<Text selectable>` の選択範囲を取得する手段が無く、同じ操作を作れない
- web だけ先行するかは、web の利用比率を見て決める。熟語は MVP の用語集でタップ 1 回で出せるため、優先度は低い

## 読み上げ

MVP に入れた。仕様と設計は [read-aloud](../read-aloud/README.md)、その先の拡張（声の選択・単語の発音・音読の評価）は [read-aloud の deferred](../read-aloud/deferred-voices-and-pronunciation.md)。

## 厳格モード

### 着手トリガー

- ランキングや他ユーザーとの比較など、**競争要素** を入れる

### 内容

| | 通常（MVP） | 厳格モード |
| --- | --- | --- |
| 時間切れ | 超過時間をカウントして解答を続けられる | 0 になったら自動で提出 |
| アシスト | 使える | 使えない |
| 一時停止 | できる（本文を隠す） | できない |
| 時間の計測 | クライアントが「画面を見ていた時間」を申告し、サーバーが壁時計で上限をかける | **サーバーの壁時計だけ** で測る（申告値を使わない） |

### 既存仕様との差分（着手時のチェックリスト）

- [ ] `reading_attempts` にモードの列を足し、開始 API でモードを受け取る
- [ ] 厳格モードでは開始 API のレスポンスから和訳・用語集を除く（クライアントで隠すだけでは不十分）
- [ ] 提出 API で、厳格モードの時間をサーバーの壁時計で計算し、締め切り後の提出を「時間切れ」として扱う
- [ ] learning-record の統計で、通常と厳格を分けて出すか決める

## ライトテーマ

- MVP はダークテーマのみ。`design-mock` で色を **デザイントークン**（背景・文字・強調・コードの配色を名前で参照）として定義しておき、ライトテーマはトークンの値の差し替えだけで済むようにする
- 着手トリガー：明るい場所（屋外・日中の mobile）で読みにくいという声が出た

## 復習モード

- 間違えた設問だけを解き直す。`attempt_answers.is_correct = false` の設問を問題単位で集めて出題する
- 単語の復習は [deferred-grammar-vocabulary](../product-overview/deferred-grammar-vocabulary.md#単語問題) の単語問題と合わせて設計する
